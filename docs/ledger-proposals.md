# Ledger proposals awaiting the maintainer

The parity documents are frozen; behavior changes enter them only as deviations-ledger entries reviewed by the maintainer. During the build, every behavior difference that the ledger does not already cover is recorded here first, in the ledger's format, and implemented as proposed. On approval each proposal becomes the next `D-` entry in `docs/parity/05-deviations-ledger.md`; on rejection the build reverts to the spec's behavior.

**P-01 · Evidence and Dispute-event scans on testnets.** Today: on testnets the ERC-1497 `Dispute` event and the `Evidence` events are read from `head − lookback` (50,000 blocks) to the latest block (spec §6.3), so for a dispute older than the lookback the Dispute event is not found, the creation time falls back, and the evidence list is empty. On mainnet and Gnosis they are read from block 0. New: every chain reads them from the arbitrator's deployment block to the latest block, chunked where the RPC caps ranges. Mainnet and Gnosis behave as today. Why: evidence older than the lookback would otherwise vanish, and the fixed lookback was a workaround for unchunked queries. Test: unit test of the scan start per chain; a Sepolia dispute older than 50,000 blocks shows its evidence.

**P-02 · What a mined write refreshes.** Today: after an appeal funding or an evidence submission, `reload()` re-reads `disputes(id)`, the evidence, `AppealDecision`, `getDispute` and the current round's contributions, but not `currentRuling`, `RulingFunded`, `appealCost`, `appealPeriod` or the withdrawable amount (spec §5.3); after a withdrawal nothing is reloaded (spec §5.15). New: the refresh runs once the transaction is mined (D-07); after a funding it also refreshes `currentRuling`, `appealCost`, `appealPeriod` and `RulingFunded`, which core reads together with the values `reload()` refreshes; after a withdrawal sequence (D-51) the withdrawable amount is refreshed. Why: core's read granularity bundles these values, and a withdraw panel that keeps showing an amount already withdrawn invites a second, empty transaction. Test: component tests: after a mined funding the panel shows the refreshed totals; after the mined withdrawals the panel shows nothing withdrawable.

**P-03 · Network switching from the unsupported-network screen and the header.** Today: clicking a network on the unsupported-network screen calls `wallet_switchEthereumChain`; any failure, including having no wallet, is only logged, and there is no `wallet_addEthereumChain` fallback (spec §2.5). New: switching uses wagmi's `switchChain`, which offers `wallet_addEthereumChain` when the wallet does not know the chain; a rejected, failed or impossible switch (no wallet connected) is shown inline. The same applies to the header's offer to switch to the page chain (D-48). Why: a silent failure leaves the user with no feedback, and wagmi's add-chain fallback cannot be separated from its `switchChain`. Test: component tests with a rejected switch and with no wallet; Playwright with a wallet that lacks the chain.

**P-04 · No "refuse to arbitrate" card for governors.** Today: every dispute except the Unslashed contracts gets an "Invalid / Refused to Arbitrate / Tied" card for ruling 0 (spec §5.12 card set item 1), governors included; their cards call the IDisputeResolver `fundAppeal`, which governors do not have (D-47 "Today"). New: the governor dialect's crowdfunding panel omits the ruling-0 card; every card it shows funds list `ruling − 1` through `fundAppeal(listIndex)`. Why: the verified KlerosGovernor source maps ruling r to list index r − 1 (`winner == _submissionID + 1`) and has no list for ruling 0, so under D-47's fixed governor funding the card's Fund action can never succeed (`writes.buildFundAppealCall` refuses it with `ruling-out-of-range`). Test: unit test that a period-3 governor panel's cards are exactly codes 1…n (`appeals/panel.test.ts`); live-tier governor dispute in the appeal period.
Code state: `appeals/panel.ts:28-30, 54` already filters the cards; `writes/appeal.ts:31-35` refuses ruling 0. The behavior ships, so the entry is needed whether or not the maintainer accepts it (on rejection, drop the filter and let web show the refusal).

**P-05 · Shared multiplier for governor ties.** Today: when the current ruling is 0, every option is a loser (§5.12 "Amounts and deadlines": a winner is only the current ruling, or any option for Unslashed), so each list costs `appealCost + appealCost × loserMultiplier / denominator` with the loser deadline `start + (end − start) × loserAppealPeriodMultiplier / denominator`; governors expose no `loserAppealPeriodMultiplier`, so §10.9's fallback `denominator / 2` puts the deadline at the half-way point. New: for the governor dialect with current ruling 0, every list costs `appealCost + appealCost × sharedMultiplier / MULTIPLIER_DIVISOR` and its deadline is the end of the appeal period. `sharedMultiplier()` (selector `0xce1d8ab2`, present as a PUSH4 operand in the recorded bytecode of poh.eth, ubi-voting.eth and kleros.eth, `families/__fixtures__/bytecode-1.json`) joins `governorAbi`, `readMultipliers` and 06 §1 row 3's getter list. Why: with D-47 governor funding works, and `KlerosGovernor.fundAppeal` charges `sharedMultiplier` with no half-period limit when `currentRuling == 0` (`node_modules/@kleros/kleros/contracts/kleros/KlerosGovernor.sol`); the panel would otherwise ask for the loser total (3,000 instead of 2,000 in the reviewer's example), close funding at half the period while the contract accepts funds to the end, and show a fully funded list as 66.66%. Test: `appeals/amounts.test.ts` governor tie case; recorded `sharedMultiplier()` replies of the deployed governors with their block; a governor golden or live case with ruling 0 if one exists.
Code state: implemented in the hand-over between phases 3 and 4 (orchestrator decision: without it, D-47's governor funding asks for the wrong amount and closes early).

**P-06 · Decision text when no title matches the ruling.** Today: the decision alert interpolates reality-eth-lib's `getAnswerString` into a template string (§5.9; `src/components/disputeDetails.js` `renderDecisionAlerts`); for a single-select ruling past the last title (for example ruling 3 with two titles) the library returns `undefined`, and the alert reads "Jury decision: undefined" / "Winner: undefined". New: such a ruling reads as its decimal value ("3"), like a formatting error; the empty labels the library returns as strings ("" for an empty title, an empty multiple-select selection, or a type it does not render) are shown as today. Why: "undefined" is an artifact of string interpolation, and §5.9 already falls back to the raw ruling when formatting fails. Test: `rulings/format.test.ts` single-select ruling beyond the titles.
Code state: `rulings/format.ts:103` with `rulings/realityLib.ts:60-71` (after review finding R6 the empty-string cases match today; only `undefined` differs).

**P-07 · Relative display and attachment URIs must be content-addressed.** Today: a display URI without `://` goes through `urlNormalize` to the gateway (§9.4 "Source"), and so does every attachment and the meta-evidence `fileURI` link (§5.6, §5.14, A10): `/ipns/<name>` becomes a gateway IPNS URL and renders mutable content in the evidence-display iframe or as a link; a bare `report.pdf` or `./display/index.html` becomes `<gateway>/ipfs/report.pdf`, a dead link. New: a relative value is served from the gateway only when `normalizeIpfsPath` accepts it; otherwise no evidence-display iframe renders and the attachment is shown as text. Absolute https URLs keep §9.4/D-26 behavior. Why: one normalizer for every gateway URL (B18), the mutable-pointer threat of A3 (IPNS), and D-26's "the result must still pass the content-addressing check"; the other values only produced dead gateway links. Test: `uri/display.test.ts` "D-26: a display path that is not content-addressed is never served from the gateway"; `uri/links.test.ts` (B19 dangerous schemes and paths shown as text).
Code state: `uri/display.ts:119-126`, `uri/attachment.ts:141-148`. No golden case is known to use such a value; the entry makes the difference explicit for the parity gate.

**P-08 · Zeroed dispute struct means "does not exist".** Today: on Gnosis and Chiado, KlerosLiquid keeps disputes in a mapping, so `disputes(id)` for an ID never created returns a zeroed struct instead of reverting (recorded in `disputes/__fixtures__/arbitrator-100.json`); the app takes `arbitrated = 0x0000…0000` as a real arbitrable and renders the case page for it (meta-evidence fails to load) instead of "Dispute with ID {id} does not exist on this network." (§5.4, §11.1 describe that screen, which only chains whose read reverts reach). New: a struct whose `arbitrated` is the zero address is the not-found state on every chain. Why: the intent of §5.4 and D-53; a zero arbitrable cannot be read or written. Test: `disputes/lookup.test.ts` with the recorded Gnosis zero struct; Playwright search for an unused Gnosis ID.
Code state: `disputes/struct.ts:28-30`, `disputes/lookup.ts:38`. (The code matches the spec's text; the proposal records that production differs on these two chains, so the parity gate does not flag it.)

**P-09 · Descriptions paired with option titles.** Today: descriptions are stored with an index splice on a possibly shorter array (`onArrayStateVariableChange`, `src/components/createForm.js:139-143`), so a description typed for option 3 before options 1 and 2 lands at index 0 and shows under option 1, and the written `rulingOptions.descriptions` can be shorter than `titles` (§4.3, §4.5 step 4). New: `descriptions` has one entry per title, at its option's index, `""` where none was typed. Why: the same mispairing defect D-08 fixes for party aliases (B20); misplaced descriptions mislead jurors. Test: `create/metaEvidence.test.ts` (option 3 described alone keeps its index; length equals titles). Note for the maintainer: under §5.13 a `""` entry is "defined", so today's question panel would print "Option i - Title:" with nothing after the colon for disputes created this way; dropping trailing empty entries would avoid that for the common case. Orchestrator decision: trailing empty entries are dropped, so `descriptions` never extends past the last described option.
Code state: `create/metaEvidence.ts`, `create/validate.ts`. Trimming to the chosen count and `descriptions: []` for uint/datetime ([129]) are already Q8/D-08 and need no entry.

**P-10 · Bracketed text, footnotes and backslashes in descriptions.** Today: descriptions and evidence descriptions render with `react-markdown` 4 on `remark-parse` 5 (spec §5.6); bracketed text with no matching link definition becomes a link to the current page (`href=""`) with its brackets dropped (`See [1] and [the rules].` renders "See 1 and the rules." with "1" and "the rules" linked; `a[0]` renders "a0"; a footnote marker `[^1]` renders a linked "^1" and its definition `[^1]: text` renders "^1: text"; an empty task marker `- [x]` renders a linked "x"); a backslash before `<` stays visible, and so does a backslash at the end of a line. New: `react-markdown` 9 parses CommonMark plus the in-house `legacyGfm` subset; bracketed text without a definition renders as today's plain text (brackets dropped) but is not a link (orchestrator decision, the variant closest to today); `\<` is an escape and renders "<"; a backslash before a line ending is a hard line break. Why: today's empty-href links lead nowhere; keeping today's text keeps the parity snapshot's `descriptionText` equal for the common `[1]` style, while the backslash cases follow CommonMark. Test: `safe-content/SafeMarkdown.corpus.test.tsx` entries for undefined references, footnotes, task markers and backslashes, including `See [1] and a[0].` recorded with `react-markdown` 4.2.2.

**P-11 · Legacy interact link with an ID that does not parse.** Today: `/:chainId/interact/:id` redirects to `/:chainId/cases/:id` for any segment (spec §1.2), so `/1/interact/abc` lands on `/1/cases/abc` and shows "Dispute with ID abc does not exist on this network." Why: A19 builds navigation targets only from a validated chain ID and a numeric dispute ID, so the raw segment is never carried into a target. **P-14 · The current ruling is read exactly.** Today: for questions other than hash, the decision alert reads the current ruling through `String(parseInt(currentRuling))` (spec §5.9), and the formatter turns the exponent string back into a number, so any ruling above 2⁵³ is rounded. The reserved Reality ruling 2²⁵⁶−1 ("Answered Too Soon") rounds to 2²⁵⁶, so `ruling − 1` becomes reality-eth-lib's invalid answer and the alert reads "Winner: Invalid", while the crowdfunding card for the same code reads "Answered Too Soon" (mainnet 1650 and 1657, both ruled 2²⁵⁶−1 on-chain). New: the ruling is read as an exact integer, so ruling 2²⁵⁶−1 reads "Answered too soon", reality-eth-lib's own label, which spec §5.9 already uses. Why: production shows the wrong answer for a ruling recorded on-chain. Test: `rulings/format.test.ts` (maximum ruling on a select question); golden cases mainnet 1650 and 1657 accept this difference under P-14.

**P-16 · Fail fast when the script runner frame never starts (not implemented).** Today: if the runner frame cannot load (for example a content-blocking browser extension cancels the request for `/__runner/index.html`), the browser still fires `load` on an error page, the host posts into it, nothing answers, and the case page waits out the whole 120 s meta-evidence budget before rendering without the script output (D-38). **P-17 · Court policy URIs must be https or content-addressed.** Today: a policy URI containing `http` is fetched as is, and a fetch or JSON error yields an `undefined` entry (spec §2.2, §6.4); any other non-empty URI is fetched as `IPFS_GATEWAY + uri`. So `http://host/policy.json` is fetched as is, `/ipns/<name>/policy.json` and a bare `policy.json` are fetched from the gateway, and a content-addressed path that contains "http" (`/ipfs/<CID>/http-policy.json`) is fetched as a relative URL against the app's own origin, which fails. Checklist B7 accepts court policies as "fetched as today". New: an https URL is fetched as is and a path that `normalizeIpfsPath` accepts is fetched through the gateway; anything else (an `http://` URL, an IPNS path, a bare relative path, a path with dot segments) is not fetched, and that court's name is unavailable, the per-court degradation of D-19. A content-addressed path containing "http" goes through the gateway and its name shows. Why: one normalizer for every gateway URL (B18) and the mutable-pointer threat of A3 for IPNS. An `http://` fetch from the https app is blocked as mixed content (and by C2's `connect-src` once enforced), so today it already fails and shows no name; refusing it changes nothing visible. The "contains http" content-addressed path was a dead relative fetch. Every policy URI recorded on mainnet and Gnosis resolves under the new rule; Sepolia and Chiado policies are not recorded and were not checked. Test: `uri/gateway.test.ts` "P-17: refuses a policy URI that is neither https nor content-addressed", "P-17: a content-addressed path containing 'http' goes through the gateway" and "B7: every court policy URI recorded on chains 1 and 100 resolves through the gateway"; `disputes/courts.test.ts` "D-19, P-17: a policy URI that is neither https nor content-addressed is never fetched".
Code state: `uri/gateway.ts` `policyFetchUrl`, `disputes/courts.ts` `readPolicy`; `packages/core/MODULES.md` §6.4 row.

**P-23 · Bound the parse cost of hostile descriptions (not implemented).** Today: react-markdown 4 on remark-parse 5 parses any meta-evidence or evidence description in full (spec §5.6). New, if approved: the description is parsed off the main thread with a time budget, and a description that exceeds it is shown as plain text with a note; or, more simply, only the first N KB are parsed and the rest is replaced by a "Description truncated" note. Why: D-42's current react-markdown parses with micromark, which is super-linear on some hostile inputs. Measured on the same inputs, old stack against new, browser render path (jsdom, production React): `"https://a.co/" + "*b*".repeat(30000)` 0.45 s against 8.6 s; `"[a]".repeat(30000)` 0.85 s against 4.0 s; `"~~[a]".repeat(20000)` 1.3 s against 3.9 s; `"*a ".repeat(800) + " a*".repeat(800)` 0.05 s against 1.6 s; but `"[".repeat(50000) + "x" + "]".repeat(50000)` 29.5 s against 3.5 s, and 2,000 nested blockquotes throw in the old stack and render in the new. The worst case measured is therefore better than today (29.5 s against 8.6 s), but some inputs are slower; the time is micromark's, not the in-house `legacyGfm` plugin's (its own quadratic paths were fixed and are tested in linear time). A description only an arbitrable's author controls can freeze the viewer's tab for seconds in both apps. The off-thread option needs a dependency decision (rendering a hast tree outside react-markdown), so it is recorded here rather than built. Test, if approved: hostile inputs render within a budget, and an over-budget description shows the plain-text fallback.
