# Rebuild the Dispute Resolver from scratch, in this repository, against a frozen behavioral spec

The current app is React 17 on Create React App 4 (the build needs `--openssl-legacy-provider`), written mostly as class components around a 1,377-line `src/app.js` that owns the routing, every transaction and most chain reads (the Reality.eth lookups, the appeal-fee multiplier reads and the smart-contract-wallet check make their own RPC calls). It carries three overlapping CSS stacks (antd 4, bootstrap 5 with react-bootstrap 1, and bootstrap 4.3 CSS from a CDN), three chain libraries (ethers 6, web3 1 and an unused `@alch/alchemy-web3`) plus `@kleros/archon`, and no CI that runs tests. The security controls added through 2025 and 2026 (content-addressed URIs, the pinned dynamic-script allowlist, on-chain Reality.eth ruling derivation, the RPC read/write split) are sound in intent but sit on this foundation; content addressing and the RPC split have no tests at all. We decided to rebuild the application rather than migrate it, keep the rebuild in this repository on one integration branch, and define "done" as parity with a written behavioral spec rather than with the old code.

## Decision

- A new application tree replaces the root of the repository on a single long-lived integration branch. A Netlify branch deploy of that branch (or the deploy preview of a draft pull request from it) is the parallel environment; cutover is the merge to master; rollback is Netlify's deploy history.
- Two tiers of code. The Reality.eth pipeline (`reality-question`, `reality-safe-question`, `reality-ruling-options`, the proxy registry, the generated known-questions map and its generator, the duplicate-key JSON guard) is ported with its 75 existing tests (39 question lookup, 23 safe template population, 9 ruling derivation, 4 JSON guard), which run without network access (the lookup tests mock the RPC layer) and include the real attack questions. The proxy entries move into the arbitrable registry of ADR 0003 with their fields unchanged. Everything else is rebuilt test-first: the URL and content-ID (CID) validation, the appeal-fee multipliers, the Atlas upload and sign-in client, and the dynamic-script sandbox (ADR 0004) have no tests today, the dynamic-script allowlist has only a three-case lookup test, and the content-addressing check was found bypassable (below).
- Five weaknesses verified on master are fixed in the rewrite and deliberately not patched on master, because the rewrite is the next release: dynamic-script results can be spoofed by any window through the global `window.onmessage`; the content-addressing check accepts `/ipfs/<CID>/../../ipns/…` and so resolves to mutable content; no check that the wallet's chain equals the page's chain precedes a signature; script parameters are embedded in HTML with chain IDs taken unvalidated from the meta-evidence; allowlisted scripts run with the app's own origin. Each is a row in the security checklist.
- "No functional regressions" is measured against `docs/parity/`, written before any rewrite code: a per-screen behavioral spec of the current app, a security-controls checklist (including the response headers the new app ships and the one path exempt from them, the script runner of ADR 0004), a golden-case list of real disputes, and a deviations ledger. The spec is frozen before UI work starts, meaning it changes only through a ledger entry. The 13 known quirks of the current app (silent transaction failures among them), listed in the deviations ledger, are all fixed, not reproduced; any other latent bug the rewrite fixes is a ledger entry too.
- Parity covers every chain the app configures today except Görli (5), Mumbai (80001) and the dead arbitrator rows for chains 3, 4, 42 and 77, which are dropped; a test guarantees that every Reality.eth home chain the registry references keeps an RPC configured, because cross-chain disputes depend on it. Meta-evidence keeps coming from the Kleros meta-evidence API, trusted as it is today; cross-checking it against the on-chain event is a later hardening.
- The production bundle contains no test-only code paths: no fixture modes, mock providers or flags that swap in fake data. Cases the golden suite needs that do not exist on-chain (multiple-select, uint and datetime questions, a dispute funded through to withdrawal) are created as real disputes on Sepolia.
- Core logic ships first with its tests; the UI comes last with its own checks.
- URLs are part of the contract: `/:chainId/ongoing`, `/:chainId/create`, `/:chainId/cases/:id?` and the redirects (`/`, `/:chainId` and `/:chainId/disputes` to `ongoing`; `/:chainId/interact/:id` to `cases/:id`) work as intended. `/:chainId/` and `/:chainId/disputes` land on a 404 today because of a relative redirect; that fix is a ledger entry.

## Considered options

- **Incremental migration** (swap the bundler, then convert component by component). Rejected: `src/app.js`, which owns the transactions and most reads, would survive most of the migration; every intermediate state is a partially migrated app that still has to ship securely; and the ethereum layer would be rewritten twice (once to fit the old shape, once to fit the new).
- **Finish and merge `feat/ui-overhaul`, then modernize.** Rejected: that branch is a restyle on the same React 17 and CRA stack, is nine commits behind master and lacks four changes merged after it forked, three of them security changes (PRs #300, #301, #304) plus the appeal-rewards wording fix (#303), and it ships a fixture mode whose code is always in the production bundle and is turned on by a build environment variable (`REACT_APP_USE_FIXTURES`), so a single Netlify build setting would serve fake data, stubbed transactions and a bypassed sign-in. It is mined for UX states, copy and validation rules only.
- **A new repository.** Rejected: it would detach the history, the open issues, the Netlify site, SonarCloud and CodeQL for no technical gain.

## Consequences

- Nothing merges to master until every row of the security checklist is green and the golden cases render equivalently on the branch deploy.
- The old application is reference material, not a dependency; nothing in the new tree imports from it.
- The module breakdown inside each package and the build workflow are decided separately, after the parity documents exist; the spec is the contract the builders work against.
