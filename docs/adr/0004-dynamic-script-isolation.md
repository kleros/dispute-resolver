# Dynamic scripts run in a dedicated opaque-origin runner page that declares UTF-8; `allow-same-origin` is never granted to a script

Meta-evidence may name a `dynamicScriptURI`, a script the resolver runs to compute ruling options and links for a dispute. Today the script runs in an iframe built by the `iframe` npm package (v1.0.0, last released April 2016) as a `blob:` document, with `sandbox="allow-scripts"` plus `allow-same-origin` when the arbitrable is on the arbitrable allowlist. A `blob:` frame with `allow-same-origin` has the app's own origin: a probe script run in the current runner could read `parent.document` and `parent.localStorage`, where the Atlas sign-in token lives today (in the rewrite it moves to session storage, which a same-origin frame can read just as well). Results come back through a global `window.onmessage` that accepts any message tagged `target: "script"` from any window, and script parameters are embedded in the frame's HTML with `JSON.stringify`, with chain IDs taken from the meta-evidence unvalidated. Removing `allow-same-origin` naively makes Reality.eth renderer scripts return `{}`; that observed breakage, not any recorded rationale, is what kept the flag in place. The cause, a missing charset, is set out below; this decision removes the flag and fixes the cause.

## What the flag was actually doing

Git and pull-request history record no reason for granting it. The flag first appeared in September 2023 on the evidence-display iframe (commit c7e3cd0, PR #172), copied from kleros/court PR #382, whose description is empty, and reached dynamic scripts in November 2025 (commit 1725c97) by copying that ternary verbatim. Empirically, the `iframe` package's blob document declares no charset. A same-origin frame inherits the app's UTF-8; an opaque-origin frame falls back to windows-1252, so a literal non-ASCII character in a script is decoded wrongly. Reality renderers that embed the `␟` delimiter literally (`QmQGMR…`, verified) then fail to parse the question JSON and return `{}`; renderers that write it as an escape sequence are unaffected. With `<meta charset="utf-8">` in the frame, the same script under `allow-scripts` alone returns the correct ruling options. On mainnet and Gnosis at HEAD no Reality script runs with the flag: registered proxies skip their scripts (ADR 0003), and the unregistered Reality arbitrables there are not allowlisted, so they already run strictly and already return `{}` for the literal-delimiter renderers. On the testnets the picture differs: the proxy registry has no Sepolia or Chiado entries while their Reality proxies are on the arbitrable allowlist, so their renderers may run with the flag today; the gate below covers them. All 30 scripts on the current allowlist (29 once the dispute 1621 override goes, see ADR 0003) were scanned statically: none reference cookies, `window.parent` or `window.top`; their `localStorage` references are vendor code that is unreached or wrapped in try/catch. RPC calls from a null origin are accepted by every endpoint tested (Alchemy, the Gnosis gateway, the IPFS CDN, the Infura key in the 1621 override); governor, Proof of Humanity and default scripts return identical results in both modes.

## Decision

- Scripts run in a dedicated static runner page in `web` (`/__runner/index.html`, a path that no app route pattern matches), loaded by its same-origin URL into an iframe with `sandbox="allow-scripts"` and nothing else, which gives the frame an opaque origin. The page declares `<meta charset="utf-8">`. It is served with its own Content-Security-Policy header, permissive about evaluating code (it must run untrusted scripts) but carrying the `sandbox allow-scripts` directive, so the page has an opaque origin however it is loaded, even opened top-level by another site, and `frame-ancestors 'self'`, so only the app can frame it. That policy is delivered as an enforced `Content-Security-Policy` response header from the runner's first deploy, never report-only and never as a `<meta>` element, because both ignore `sandbox` and `frame-ancestors`; the app-wide report-only rollout of the security checklist does not apply to it. The runner's bootstrap does not rely on the headers alone: it evaluates nothing unless `self.origin === "null"` (proof that the document really is sandboxed), refuses to run as the top-level window, and accepts the script and parameters only through a port whose message has `event.source === window.parent` and `event.origin === location.origin` (the URL's origin is the app's even inside an opaque document). The runner path is the one exception to the `frame-ancestors 'none'` and strict policy of the security checklist, which are attached to the enumerated app route patterns rather than to a catch-all, because Netlify's header rules have no path negation; headers that are harmless to the runner (`nosniff`, referrer and permissions policies, `X-Frame-Options: SAMEORIGIN`) go on every path. A deploy test splits the runner's policy value on commas and asserts exactly one policy, containing `sandbox allow-scripts` without `allow-same-origin` and `frame-ancestors 'self'`, and that no app path's policy contains the runner's eval allowance. A further test loads the runner without the sandbox attribute and from a non-app parent and asserts that nothing is evaluated. The application's strict policy is untouched; a `srcdoc` or `blob:` frame would inherit it and force `unsafe-eval` onto the whole app. The `iframe` package is dropped.
- Nothing untrusted is embedded in HTML. The host sets the `sandbox` attribute before `src`, waits for the frame to load, and posts the script text, the validated parameters and one end of a fresh `MessageChannel` to the frame's window with target origin `'*'` (the only value an opaque origin accepts); only the port carries results back. The runner's fixed bootstrap defines the globals the pinned scripts rely on (`scriptParameters`, `resolveScript`, `rejectScript`), installs the RPC redirect (now matching provider hosts by pattern, so a script that hardcodes a known provider with a dead key is repaired whichever key it used) and the duplicate-key JSON guard for Reality scripts (Reality questions can override template keys through duplicate JSON keys), evaluates the script text, and calls `getMetaEvidence()`. The script-facing contract is therefore unchanged. Chain IDs are validated as integers before use. This removes `</script>` injection through meta-evidence parameters and through the script body alike.
- The host accepts a result only from that run's port, so there is no global handler, concurrent runs cannot cross-resolve, and no other window can inject a result. The frame is removed when the run settles or the run timeout fires (a script that throws never reports, so the run must settle on its own).
- The pinned script allowlist stays. Adding a script to it requires running the script in this runner first, which surfaces any dependence on parent storage or DOM.
- The arbitrable allowlist no longer plays any role in script sandboxing. It remains, with its membership unchanged, as the sole input to evidence-display iframe flags until the test described under Scope.

## Gate before cutover

Three checks, all required: a unit test that a script containing a non-ASCII literal round-trips in the runner; the Reality renderer `QmQGMR…` run against mainnet dispute 1650 (a Seer prediction-market question; its proxy is registered, so mainnet never runs this script, but it is the known charset-sensitive one) as a runner regression test; and every allowlisted script referenced by at least one existing dispute on a supported chain, ongoing or resolved, executed in both the old runner and the new one, with identical outputs wherever production produces a result. A production result that is empty (`{}`) or charset-garbled counts as a failure, so the new runner may succeed there, and each such case is reviewed and recorded in the deviations ledger. Any other difference blocks the change. The Graph endpoints used by the Moderate and Sepolia Curate scripts were not CORS-tested and are covered by this gate; the read-only RPC configured per deployment, which the redirect targets, must not restrict origins, which the security checklist records as a deploy requirement.

## Scope

This decision covers dynamic scripts only. Evidence displays of the allowlisted arbitrables are served from other origins (the IPFS gateway or the Proof of Humanity app host), so `allow-same-origin` there never reaches the app; it only lets a display keep its own origin and storage. The code does not enforce that, so the rewrite must reject a display URL whose origin equals the app's before granting the flag. The T2CR display rendered identically without the flag in one A/B check (dispute 300), but Proof of Humanity v2 and Curate displays were not tested and may read storage on boot. Their flags stay as they are until an A/B test on the branch deploy, and tighten only for what passes.

## Considered options

- **Keep `allow-same-origin` for allowlisted arbitrables.** Rejected: the content-ID allowlist would remain the only barrier between an allowlisted script and the whole application, for a privilege no script uses.
- **Run scripts in a Web Worker.** Rejected: the bundled scripts and their bootstrap reference `window` and `window.parent`, which do not exist in a worker.
- **Keep the `iframe` package and pass a `head` with the charset**, or **use a `srcdoc` frame.** Workable for the charset, rejected: both inherit the application's Content-Security-Policy, and both still inline the script body into HTML.

## Consequences

- A future allowlisted script that needs parent storage or DOM fails visibly rather than running with the app's origin.
- Scripts that hardcode a dead host that is not a known RPC provider (the old `ipfs.kleros.io` gateway in the Sepolia Curate scripts) still fail, as they do now.
- Scripts' network requests carry `Origin: null`; an endpoint with an origin allowlist would refuse them. None of the endpoints tested does.

## Amendment (2026-10-20, P-16)

The runner acknowledges a run before it evaluates anything. On the run's port, the bootstrap first posts `{ type: "dr-runner/accepted" }`, and it posts nothing for a request it refuses. The host gives each frame an acknowledgement window of 5 s, counted from the frame's append. If no acknowledgement arrives in that window, the run settles as a runner error and the frame is removed, so a runner page that a content blocker or a captive portal keeps from starting fails within seconds instead of after the 120 s meta-evidence budget. Core treats a runner error as final. The request message's protocol version is 2. Results still come back only through the port, and a result without an acknowledgement is still accepted. See P-16 in `docs/ledger-proposals.md`.
