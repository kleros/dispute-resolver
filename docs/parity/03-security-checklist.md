# Security checklist

Nothing merges to master until every row below is **green**: implemented in the named home, with the named test passing, reviewed by someone other than the author. Columns: what the control does, what it protects against, where it lives today, where it lives in the new app (`core` package, `web` package, or `deploy` configuration), the test that proves it, and status.

Status values: `port` (carry over, behavior unchanged), `fix` (weakness closed; the ledger entry is named), `new` (hardening added by the rewrite), `accepted` (known weakness kept, with the reason), `deferred` (not in this release, with the reason). For `accepted` and `deferred` rows, which have no home or test, green means the acceptance was reviewed and the reason still holds.

**Trust model.** Trusted: the configured RPC endpoints, the IPFS gateway, the Kleros meta-evidence API, Atlas, the registry data in `core`. Untrusted: meta-evidence and evidence JSON, dynamic-script output, Reality.eth question parameters and templates, every arbitrable contract, the chain ID in the URL, everything the user types, and every value a third-party frame sends back.

## D. Deploy requirements (operator checklist)

- Headers file with the `/*` headers, the enumerated app route patterns and the runner exception (C1–C3).
- `REACT_APP_WALLETCONNECT_PROJECT_ID` set; existing `REACT_APP_*` RPC variables unchanged; optional `REACT_APP_PUBLIC_RPC_<chain>` for keyless injection (B13).
- Every read and public RPC passes the pre-flight for range caps and null-origin CORS (C10).
- Netlify `CI=true`; build command and publish directory updated for the workspace layout.
- The generator `--check` for the Reality known-questions map run before the release (A6).
